# T037 — MFA quando o dispositivo é novo, sem alterar a base de dados

## Contexto

O operador: «implementar o MFA quando o dispositivo de onde o utilizador
liga é novo? Isso **sem alterar a base de dados**».

A restrição é a parte interessante. A base de produção é o WHMCS 5.3.9
importado, e **não se lhe toca**.

## Reconhecimento

| Facto | Evidência |
|-------|-----------|
| **Não há** tabela de 2FA nem de dispositivos | `information_schema` — nenhuma tabela com `twofact`, `2fa`, `device`, `trust` ou `token` |
| `tblclients.authdata` é um `text` **vazio** em todos os clientes | `SELECT authdata, LENGTH(authdata)` → `''`, `0` |
| `tblclients.authmodule` também está vazio | idem |
| A WHMCS 6/7 usa `authdata` para o segredo 2FA | é a convenção do próprio WHMCS |
| A sessão é um `PHPSESSID` | `session_regenerate_id(true)` no login |
| O `cc_encryption_hash` está no ambiente | `CC_ENCRYPTION_HASH` — o segredo partilhado com o WHMCS |
| A app já tem `shared_preferences` | para a sessão |

## A restrição, transformada em desenho

O MFA precisa de guardar **duas** coisas: o segredo 2FA do utilizador, e
a lista de dispositivos de confiança.

**O segredo** vai para `tblclients.authdata` — uma coluna que **já
existe**, e que o WHMCS 6/7 usa exactamente para isto. Nenhuma coluna
nova, nenhuma tabela nova.

**Os dispositivos de confiança** não precisam de estar em lado nenhum:
o servidor emite um **cookie assinado** (HMAC) com o identificador do
dispositivo e a validade. Quem tem o cookie **e** a assinatura certa
é um dispositivo de confiança. Não há lista para guardar, nenhuma
consulta extra, e revogar um dispositivo é o cookie expirar.

O **desafio** do MFA (o "estás a pedir um segundo factor, prova-o")
é um token assinado, de vida curta, que carrega o cliente e o
desafio — também sem armazenamento.

## Scope

### In scope

**O servidor**
- `TotpService` — RFC 6238 (SHA-1, 6 dígitos, 30 s), com janela de ±1
- `MfaService` — a inscrição, o desafio, a verificação
- `DeviceTrust` — o cookie assinado
- API: inscrição, confirmação, estado, e o desafio no login

**A app**
- O ecrã **Segurança**: o estado, a inscrição (com QR), a confirmação
- O login: quando o servidor pede o segundo factor, o ecrã pede o
  código
- O **identificador do dispositivo**, guardado no dispositivo

### Out of scope

- A2F por correio (o correio do host é para a recuperação; o TOTP é
  mais forte e não precisa de rede)
- A gestão dos dispositivos de confiança pelo cliente (revogar todos)
- A administração do 2FA de um cliente pelo painel
- **Alterar o esquema** — é a restrição

## Acceptance Criteria

- [ ] AC1 — O segredo 2FA vive em `authdata`, e **nenhuma** coluna ou
      tabela é criada
- [ ] AC2 — O cliente pode inscrever-se (QR + confirmação por código)
- [ ] AC3 — Um login de um **dispositivo novo** exige o código
- [ ] AC4 — Um login de um **dispositivo conhecido** não o exige
- [ ] AC5 — O cookie de confiança é assinado e expira
- [ ] AC6 — O desafio é assinado e de vida curta
- [ ] AC7 — A app tem um ecrã de **Segurança**
- [ ] AC8 — O `authdata` de um cliente que não usa a nossa funcionalidade
      **não** é sobrescrito
- [ ] AC9 — Todos os portões verdes
