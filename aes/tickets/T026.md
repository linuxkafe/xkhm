# T026 — Importação dos Dados de Produção + Verificação

## Context

**Resposta directa a "a base de dados foi completamente importada?": NÃO.**

A base de dados local `linuxkonect` é um **fixture** compatível com o esquema
WHMCS (16 tabelas, dados de exemplo), criado por `docker/init.sql`. A base de
dados de produção (`10.0.3.1/linuxkonect`) **nunca foi importada** porque é
inalcançável a partir desta máquina.

### Diagnóstico (medido, não suposto)

```
$ ip route get 10.0.3.1
10.0.3.1 via 10.0.0.1 dev eno1 src 10.0.0.111

$ ip route
default via 10.0.0.1 dev eno1
10.0.0.0/24 dev eno1              ← a sub-rede local é 10.0.0.0/24
                                   ← NÃO existe rota para 10.0.3.0/24

$ traceroute 10.0.3.1
1  10.0.0.1
2  192.168.1.1                    ← o router também não conhece 10.0.3.0/24
3  37.28.216.2                    ← segue para a Internet
...
```

O pacote sai para a Internet e morre. Não é firewall nem credencial: é
**ausência de rota**. A máquina está em `10.0.0.111/24`; o servidor de base
de dados está numa rede `10.0.3.0/24` que o gateway desconhece.

O mesmo bloqueio já estava documentado no projecto whmcs (ticket T002:
"live DB `10.0.3.1:3306` unreachable from build host").

### Consequências práticas

1. O utilizador `linuxkafe` **não existe** localmente — a linha real nunca
   foi importada.
2. O contentúdo real (clientes, faturas, tickets, domínios) não existe aqui.
3. A base `whmcs` do contentor `whmcs-mysql` está **vazia** (sem tabelas).
4. Não existe nenhum dump `.sql` da produção em nenhum sítio do disco.

## Scope

### In scope

- **Ferramenta de importação**: `make db-import FILE=<dump.sql>` aplica um
  dump (`mysqldump`) na base local, incluindo o esquema — o dump traz os seus
  próprios `CREATE TABLE`, portanto **não é preciso inventar o esquema**.
- **Ferramenta de exportação**: `tools/export_prod_db.sh`, para correr **na
  máquina que alcança 10.0.3.1**, produzindo o dump.
- **Verificação pós-importação**: o `SchemaParityTest` passa a correr contra
  a base importada, e um relatório diz exactamente o que divergiu do fixture.
- **Diagnóstico de conectividade**: `make db-check` responde a três perguntas
  — o dump existe? a base responde? o esquema é o esperado?
- **Seed de desenvolvimento**: o fixture actual passa a chamar-se
  explicitamente "seed" e fica documentado como *não* sendo a produção.

### Out of scope

- Inventar o esquema WHMCS 5.3.9 à mão (risco de colunas erradas — ver
  SD-CI-002)
- Alterar a base de dados de produção
- A migração do front-end (T025)
