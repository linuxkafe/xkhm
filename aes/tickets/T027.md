# T027 — Exposição do MySQL: incidente e correcção

## Contexto

Durante o trabalho de T025 a base de dados local `linuxkonect` foi
**apagada e substituída por uma nota de resgate** (`RECOVER_YOUR_DATA_info`).

A nota indica o par `host + user: 94.61.137.133 + root`. O IP público
desta máquina é exactamente `94.61.137.133`.

## Diagnóstico

A causa é uma falha auto-infringida no `docker-compose.yml` que escrevi:

```yaml
ports:
  - "3306:3306"          # 0.0.0.0:3306 — todas as interfaces
```

Combinado com:

```yaml
- MYSQL_PASSWORD=qm9W8amh5XV9A4Dr    # a senha de PRODUÇÃO
- MYSQL_ROOT_PASSWORD=rootpassword
```

O MySQL ficava **publicado na Internet**, com uma senha que está no
histórico do git, e sem firewall que o impedisse de chegar lá. Um scanner
encontrou a porta e deixou a nota.

Verificação (antes da correcção):

```
$ docker port xkhm-mysql-1
3306/tcp -> 0.0.0.0:3306
3306/tcp -> [::]:3306

$ curl -s ifconfig.me
94.61.137.133
```

## Danos

| O que | Estado |
|-------|--------|
| Base de dados local `linuxkonect` | **restaurada** a partir de `docker/backups/` (16 tabelas, o fixture) |
| Ficheiros do sistema de ficheiros | **nenhum** — a busca por ficheiros deixados pelo atacante não devolveu nada |
| Outros contentores | **não afectados** (o `ollama` e o `searxng` continuam expostos — ver T028) |
| **Senha de produção** | **COMPROMETIDA** — está no histórico do git e no `configuration.php` |

## A correcção

1. **A porta é publicada apenas no loopback**: `127.0.0.1:3306:3306`.
2. **A base local tem as suas próprias credenciais** — `xkhm-local-only` /
   `xkhm-local-root`. A senha de produção deixou de ser a senha local.
3. **`configuration.php` aceita `DB_PASSWORD` do ambiente**, e o Apache
   passa-a com `PassEnv` (por omissão, `clear_env On` apaga o ambiente
   antes do PHP — sem isto a variável nunca chegava ao PHP).
4. As ferramentas de importação usam as credenciais locais.

## Consequences for the production deployment

The production password is in `configuration.php` and in the git history.
**It must be rotated.** The attacker states they hold a dump of the
database; the local database they took was the fixture, but the password
they used is the production one, so the production database is very likely
reachable with it from wherever the attacker is.

## Acceptance Criteria

- [ ] AC1 — MySQL is not reachable from outside the host
- [ ] AC2 — The local database has its own credentials
- [ ] AC3 — `configuration.php` still carries the production password as its
      default, and the environment variable overrides it
- [ ] AC4 — The import tooling uses the local credentials
- [ ] AC5 — The operator is told, in writing, that the production password
      must be rotated
- [ ] AC6 — The rest of the stack keeps working
- [ ] AC7 — `make test`, `make lint`, `make e2e` green
